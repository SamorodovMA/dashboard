## 1. Контекст и проблема

### 1.1 Что сейчас происходит

В компании есть **GEO-мониторинг** — автоматизированная система, которая 4 раза в день прогоняет тестовые кейсы по расписанию доставки и присылает Telegram-отчёт. Но у неё есть ограничение:

- **GEO работает только для склада Коптево**. Для остальных доноров (Сум, Браст, ДЛТ, Оксмер, Бутики) автоматической проверки нет.
- Настройки доставки проверяются **вручную на сайте (чекауте)** раз в 2–3 недели.
- Когда обнаруживается расхождение в датах, **невозможно быстро определить источник проблемы**:
  - Неправильные настройки в Axapta (расписание, капаситет, привилегия)?
  - Ошибка в тестовом кейсе GEO?
  - Ошибка в чекауте?

### 1.2 Кто будет пользоваться

| Пользователь | Роль | Как часто |
|-------------|------|-----------|
| **Сергей Гришагин** | Логист | Ежедневно |
| **Артур Боринов** | Логист | Ежедневно |
| **Ира Козлова** | Логист | Эпизодически |

### 1.3 Что нужно бизнесу

Создать **независимый инструмент**, который позволит логисту:

1. Задать параметры заказа (товар, донор, склад, способ доставки, карта, привилегия)
2. Получить расчёт плановых дат **напрямую из Axapta** в реальном времени
3. Увидеть детализацию по этапам: подбор → перемещение → упаковка → ПДО → ПДД
4. Сверить результат с GEO-мониторингом и чекаутом
5. Быстро определить, на чьей стороне проблема

## 2. Требования к API

### 2.1 Что должен делать бэкенд

Бэкенд (Axapta) должен реализовать **три эндпоинта**:

#### 2.1.1 POST /api/calculate — Расчёт расписания доставки

**Назначение**: Принимает параметры заказа, возвращает рассчитанные этапы по всем запрошенным донорам.

**Входные параметры:**

| Поле | Тип | Обязательное | Описание | Пример |
|------|-----|-------------|----------|--------|
| `product` | string | да | Артикул товара | `TEST-001` |
| `cardType` | string | да | Тип карты клиента | `White`, `Orange`, `Black` |
| `privilege` | string | да | Привилегия клиента | `VIP_online`, `Orange+`, `Black` и др. |
| `donors` | string[] | да | Список доноров для расчёта | `["Коптево", "Сум", "Браст"]` |
| `destination` | string | да | Склад комплектации | `КоптИнтмаг`, `ИнтМаг`, `ДИнтМаг` |
| `deliveryType` | string | да | Тип доставки | `ССД`, `ПВЗ` |
| `deliveryCode` | string | да | Код способа доставки | `112b`, `29b`, `100` и др. |
| `testMode` | boolean | да | Тестовый режим (по всем донорам) | `true`, `false` |

**Выходные данные (на каждый донор):**

| Этап | Что возвращаем | Примечание |
|------|---------------|------------|
| **Подбор** | start / end | Дата и время начала и окончания подбора на доноре |
| **Перемещение** | start / end | Дата и время перемещения с донора на склад комплектации |
| **Упаковка** | start / end | Дата и время упаковки на складе комплектации |
| **ПДО** | start | Предварительная дата отгрузки (только начало, end не показываем) |
| **ПДД** | start | Плановая дата доставки (только начало, end не показываем) |

**Дополнительно к каждому этапу**: код расписания (например, `LS04307829`), чтобы можно было идентифицировать, какое конкретно расписание сработало.

**Дополнительно к ответу**: лучший донор (с минимальной датой доставки) и лучшая дата доставки.

#### 2.1.2 GET /api/filters — Справочники

**Назначение**: Возвращает списки доступных значений для фильтров на фронтенде.

Что должно быть в ответе:
- Список товаров (артикулов)
- Список доноров
- Список складов комплектации
- Типы доставки (ССД, ПВЗ)
- Коды способов доставки с описаниями (сгруппированные по типу доставки)
- Типы карт клиента
- Список привилегий

#### 2.1.3 GET /api/orders/{orderId}/calculation — Детализация расчёта по заказу

**Назначение**: Возвращает уже готовый расчёт по конкретному заказу из Axapta.
Заказ уже создан в системе, и по нему уже есть рассчитанные этапы.
Этот эндпоинт нужен, чтобы логист мог быстро посмотреть детализацию по конкретному заказу, не заполняя фильтры.

**Входные параметры:**

| Поле | Тип | Обязательное | Описание | Пример |
|------|-----|-------------|----------|--------|
| `orderId` | string | да | Номер заказа в Axapta | `AX-2026-001234` |

**Выходные данные:**

| Поле | Тип | Описание |
|------|-----|----------|
| `orderId` | string | Номер заказа (эхо) |
| `product` | string | Артикул товара |
| `cardType` | string | Тип карты клиента |
| `privilege` | string | Привилегия клиента |
| `donor` | string | Донор, с которого подобран товар |
| `destination` | string | Склад комплектации |
| `deliveryType` | string | Тип доставки |
| `deliveryCode` | string | Код способа доставки |
| `stages` | Stage[] | Массив этапов обработки заказа |
| `deliveryDate` | string (ISO 8601) | Плановая дата доставки |

**Ожидаемый формат ответа:**

```json
{
  "orderId": "AX-2026-001234",
  "product": "TEST-001",
  "cardType": "White",
  "privilege": "VIP_online",
  "donor": "Коптево",
  "destination": "КоптИнтмаг",
  "deliveryType": "ССД",
  "deliveryCode": "112b",
  "stages": [
    { "name": "Подбор", "start": "2026-07-06T09:00:00Z", "end": "2026-07-06T09:30:00Z", "code": "LS04307829" },
    { "name": "Перемещение", "start": "2026-07-06T09:30:00Z", "end": "2026-07-06T10:30:00Z", "code": "LS04307829" },
    { "name": "Упаковка", "start": "2026-07-06T10:30:00Z", "end": "2026-07-06T12:00:00Z", "code": "PS01965423" },
    { "name": "ПДО", "start": "2026-07-06T12:00:00Z", "end": null, "code": "DS00832254" },
    { "name": "ПДД", "start": "2026-07-06T13:00:00Z", "end": null, "code": "DS00832254" }
  ],
  "deliveryDate": "2026-07-06T13:00:00Z"
}
```

**Обработка ошибок:**

| Ситуация | HTTP статус | Что вернуть |
|----------|-------------|-------------|
| Заказ не найден | 404 | `{ "status": 404, "message": "Заказ AX-2026-001234 не найден" }` |
| Внутренняя ошибка | 500 | Общее сообщение без деталей реализации |

### 2.2 Логика расчёта

При расчёте Axapta должна учитывать:

1. **Настройки расписаний** — какие расписания работают для данного донора, склада, способа доставки
2. **Капаситет складов** — загрузка складов, время на обработку
3. **Привилегии клиента** — VIP-клиенты могут иметь приоритетную обработку
4. **Тип карты** — влияет на доступные способы доставки и привилегии
5. **Код способа доставки** — конкретный код (например, `112b` — VIP Москва ССД ближняя зона) определяет временные слоты и условия

### 2.3 Ожидаемый формат ответа (POST /api/calculate)

```json
{
  "donors": [
    {
      "donor": "Коптево",
      "stages": [
        { "name": "Подбор", "start": "...", "end": "...", "code": "LS04307829" },
        { "name": "Перемещение", "start": "...", "end": "...", "code": "LS04307829" },
        { "name": "Упаковка", "start": "...", "end": "...", "code": "PS01965423" },
        { "name": "ПДО", "start": "...", "end": null, "code": "DS00832254" },
        { "name": "ПДД", "start": "...", "end": null, "code": "DS00832254" }
      ],
      "deliveryDate": "2026-07-06T13:00:00Z"
    }
  ],
  "bestDonor": "Коптево",
  "bestDeliveryDate": "2026-07-06T13:00:00Z",
  "destination": "КоптИнтмаг",
  "deliveryType": "ССД",
  "deliveryCode": "112b"
}
```

### 2.4 Обработка ошибок

API должно возвращать понятные сообщения об ошибках:

| Ситуация | HTTP статус | Что вернуть |
|----------|-------------|-------------|
| Неверные параметры | 400 | Описание, какое поле невалидно |
| Не найден товар/донор/склад | 400 | Сообщение, что именно не найдено |
| Заказ не найден | 404 | Сообщение, что заказ не найден |
| Внутренняя ошибка | 500 | Общее сообщение без деталей реализации |
| Таймаут расчёта | 504 | Превышено время расчёта |

## 4. Технические требования

### 4.1 Формат данных

- **Request/Response**: JSON (Content-Type: `application/json`)
- **Даты**: ISO 8601 (`YYYY-MM-DDTHH:mm:ssZ`)
- **Кодировка**: UTF-8

### 4.2 Аутентификация

_Определяется командой Axapta._ Рекомендуемые варианты:
- Basic Auth
- API Key (через заголовок `X-API-Key`)
- OAuth 2.0 Client Credentials

### 4.3 CORS

Фронтенд будет развёрнут на GitHub Pages: `https://samorodovma.github.io`

Необходимо настроить CORS для этого домена:
```
Access-Control-Allow-Origin: https://samorodovma.github.io
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type, Authorization
```

### 4.4 Производительность

- **Таймаут**: расчёт должен укладываться в 30 секунд
- **Кэширование справочников**: эндпоинт `/api/filters` можно кэшировать (фронтенд будет кэшировать на 1 час)

## 5. Критерии приёмки

API считается готовым, когда:

1. [ ] **POST /api/calculate** возвращает корректные даты для всех комбинаций донор + склад + способ доставки
2. [ ] **POST /api/calculate** корректно обрабатывает привилегии и типы карт
3. [ ] **POST /api/calculate** возвращает ошибку с понятным сообщением при невалидных параметрах
4. [ ] **GET /api/filters** возвращает актуальные справочники
5. [ ] **GET /api/health** возвращает статус доступности
6. [ ] **GET /api/orders/{orderId}/calculation** возвращает детализацию расчёта по заказу
7. [ ] **GET /api/orders/{orderId}/calculation** возвращает 404 для несуществующего заказа
8. [ ] Все эндпоинты работают через CORS с доменом GitHub Pages
9. [ ] Время ответа `/api/calculate` не превышает 30 секунд
10. [ ] Формат ответа соответствует контракту (см. [`API_CONTRACT.md`](API_CONTRACT.md))
